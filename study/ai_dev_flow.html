AI时代下开发方式的转变

AI开发模式

# AI时代下开发方式的转变

# 带来的问题

  • 敏捷开发正在失效
    • 系统稳定
    • 人力稀缺
    • 编码实现昂贵
  • AI时代
    • 工作分配困难
    • 代码生成量激增。极易产生冗余逻辑和额外分支，系统耦合度上升。维护性下降。
    • 短期交付快，长期维护难。每个人的prompt不一样，产生风格不同，生成的代码也不一样。丧失一致性。
    • 过度依赖review，修复成本高。
  • 警惕vibe coding陷阱，从爽感编码到系统性失控的工程危机，陷入虚假敏捷，陷入无尽的 vibe debugging 循环。缺乏系统规范，完全依赖【即时对话】与直觉的盲目开发模式。
    • 不可观测，黑盒交付。没人知道功能到底满足了哪些约束，只是看起来能跑。
    • 不可复制。换个人，换个提示词，实现逻辑不一样，无法标准化推广。
    • 不可维护。模块边界混乱，技术债积累，重构成本高。

# 交付内容的改变

  • 代码变得廉价。
  • 规范与约束、目标与价值、决策质量。
  • 从交付节奏，转向价值流系统。
  • 做了很多事，不等于做了对的事。
  • 交付很多需求，不等于系统朝正确方向演化。
  • 衡量标准，不仅仅是贡献多少代码，而是参与到AI和人的协同中。
  • 不要问“项目何时结束”，要问“系统如何持续进化”。

# 该做什么

  • 不再关注于拆任务，模块怎么写。
  • 把问题讲清楚，系统边界，高质量可检验的决策。
  • 定义要实现什么，为什么这么设计。
  • 清晰的决策变得昂贵。
    • 定义目标与价值：我们究竟要实现什么？为什么是现在做？
    • 规范与约束：把模糊的意图，转化为AI能精准执行的严谨规范。
    • 决策质量：基于数据反馈，做出高质量的系统取舍与迭代。

# 方法论升级

# 规范驱动开发SDD: Specify Drive Development

  • 用规范驯服生成式AI。要做什么，怎么约束，验收标准是什么写清楚。
  • 人力聚焦在：写规范，审规范，审生成物。
    • 规范优先
    • AI起草，人类裁决：审核架构与合规
    • 可复用资产：沉淀标准化模板与实践。

# Github四步法

# Specify: 需求与规范。

  • 核心产出：结构化需求和规范
    • AI:起草草案，补全边界与示例
    • 人：定义目标，审核修订规范

# Plan: 方案与架构

  • 核心产出：技术方案与架构决策
    • AI: 生成架构方案与权衡分析
    • 人：架构评审，做技术取舍

# Tasks：任务拆解

  • 核心产出：任务清单与测试项
    • AI: 拆解为具体开发/测试任务
    • 人：粒度调整，分配Agent

# Implement:实现与验证

  • 核心产出：代码实现，文档与用例

    • AI:生成代码、测试、基础文档
    • 人：代码审查，集成与验收

  • 注意：遇到问题，严谨裸改代码，需回溯修正 Spec 或 Plan，确保文档与代码一致。

# Agent小组

  • 从人机辅助进化为自治的Agent小组

  • 猜想

    • 通过已有的项目来产出规范
    • 通过产品文档来产出需求文档
    • 通过测试文档来产出测试任务

  • 人 + 多 Agent 模式

    • 规范助手，Specify阶段
    • 方案助手，Plan阶段
    • 任务拆解，Tasks阶段
    • 质量守卫，Implement阶段

    # 开发者的角色转变

    • 从【手写代码】到【编排智能】的身份跃迁
    • 未来最贵的不是键盘敲得快的人，而是能把一群Agent指挥得当的人。

    # 结构化定义能力

    • 将业务需求转化为严谨的Prompt与边界条件。
    • 清晰定义目标和验收标准，让AI无法误解。

    # 审查

    • 从正确性、安全性到代码风格的一致性，对AI输出的最终质量负责。
    • 业务逻辑是否正确。

    # 系统架构思维

    • 跳出局部代码。
    • 关注改动是否引入技术债，是否有利于未来Agent系统的长期演化与协作。

    # AI产品经理

    • 自己能把产品跑起来，包括前端交互和后端mock数据。
    • 跑起来的页面，甚至达到快速部署验证。

    # 架构师

    • 建立自动化治理机制，防止架构腐蚀。
    • 把隐形规则显性化，将约束固化为 Lint 规则和CI/CD
    • 负责度，耦合度可检测，不能指望人工检测。
    • 安全与红线治理：哪些可以引用，哪些不可用。

    # 新工种

    # 提示工程师

    • 职能：交互架构
    • 设计高质量Prompt与规范模板库
    • 业务逻辑拆解为可执行的AI步骤
    • 优化上下文拼接，确保输出可复用
