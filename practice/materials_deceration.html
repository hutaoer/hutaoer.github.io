TMS 物料装修搭建系统 — 项目架构与设计文档

# TMS 物料装修搭建系统 — 项目架构与设计文档

本文档描述工作区（tms）内各子项目的职责、设计原理与协作流程，适用于物料装修搭建相关开发与维护。

# 一、工作区概览

本工作区是一个可视化页面搭建（TMS）体系，用于通过拖拽物料完成页面装修。整体采用多仓库/多包结构，各包通过 npm 发布与引用协作。

项目 包名 职责简述
types @xy/tms-type 搭建系统类型与接口定义中心，无实现
materials @xy/demo-materials 建站物料组件库（外经贸业务物料）
setter @xy/tms-setter 属性配置面板中的编辑器（输入框、日期、上传等）
render @xy/space-render 根据 schema 渲染页面的 H5/小程序渲染器
sdk @xy/tms-sdk 搭建工作台（画布、物料面板、属性面板、撤销重做等）
space-material-layers @xy/space-material-layers 物料图层与协议空间（样式容器等）
space-materials @xy/space-materials 微前端主应用，承载搭建/预览页面

# 二、各项目说明

# 2.1 types（@xy/tms-type）

职责：TMS 搭建系统接口定义中心，为所有衍生工程提供统一的类型与协议约定，仅类型，无运行时实现。

关键类型（typings/ 下）：

  • MaterialSchema：物料属性配置面板描述协议（displayName、propsDefaultValue、containerSchema、propsSchema）
  • MaterialInfo：运行时物料协议（componentType、name、View、ViewSchema、viewType 等）
  • MaterialViewData / MaterialViewDataItem：画布上的“视图数据”，即当前页面由哪些物料实例组成、每个实例的 id、componentType、props、children 等
  • MaterialDescription：物料描述（含 View、ViewSchema、viewType、category 等）
  • PageInfo：页面级信息
  • SpaceMaterialSchema（在 space.ts）：在 MaterialSchema 基础上扩展 onInit、onSave、onPublish、beforeDropped、validators 等生命周期与校验

设计要点：所有使用“物料”“视图数据”“schema”的包都依赖 @xy/tms-type，保证协议一致。

# 2.2 materials（@xy/demo-materials）

职责：建站物料组件库，提供具体业务物料（图片、文本、轮播、导航、服务产品等）的视图组件 + 配置 Schema。

目录结构要点：

  • src/index.ts：导出各物料组件（Image、Txt、Swiper、Menu、ServiceProducts 等）
  • src/materialsComponents/<物料名>/：单物料目录
    • tms.ts：物料元信息与入口（MaterialDescription），包含 name、componentType、category、View、ViewSchema 等
    • view-schema.tsx：该物料的 ViewSchema（SpaceMaterialSchema），定义 propsDefaultValue、propsSchema、containerSchema、onSave/onPublish/beforeDropped 等
    • pc.tsx / 其他端：实际渲染组件 View

物料描述结构（tms.ts）：

{
  name: '图片',
  componentType: "Image",
  category: 'base',
  ViewSchema,                    // 配置面板与默认值
  View: { [DeviceEnum.PC]: ViewPC, [DeviceEnum.Mobile]: ..., ... }
}

ViewSchema（view-schema.tsx）：声明默认值、容器能力、右侧属性面板（通过 Field + 各种 Setter），以及 onSave/onPublish/beforeDropped 等。

多端：移动端/小程序设计宽度 750；支持 TMS 搭建产物、PC 搭建产物等（见 package.json 中 build:dist:*）。

# 2.3 setter（@xy/tms-setter）

职责：属性配置面板中的编辑器，以 npm 包形式给搭建页和物料库使用。例如：数字输入、日期、颜色、字体、边框、单选框、上传等。

入口：src/setter/index.ts 导出 style、string、number、datepicker、list、slider、font、color、space、border、borderRadius、radio、checkbox、check、background、switch、textStyle 等。

使用方式：在物料的 ViewSchema 的 propsSchema 中引用，如 <RadioSetter />、<BorderRadiusSetter />、<I18nImageSetter /> 等，由 SDK 的 Form/Field 渲染成右侧配置面板。

# 2.4 render（@xy/space-render）

职责：根据 viewData（MaterialViewData） 和 materialComponents 把页面渲染出来，用于搭建态预览和线上 H5/小程序结果展示。

核心流程：

  1. Entry：提供 RenderContext、InnerRenderContext，注入 materialComponents、viewData、pageInfo、layers 等，并做错误边界与事件派发。
  2. WebRender（web/index.tsx）：H5 渲染入口，用 ScrollView + ContainerRender 包裹。
  3. ContainerRender：按层级递归渲染容器（使用 ContainerLayout）。
  4. ViewItemRender：根据 viewItem.componentType 从 materialComponents 取组件，注入 props（含 $API.ContainerRender），再套 layers，得到单个物料实例的 React 节点。

设计要点：

  • 渲染仅依赖 viewData + materialComponents，与搭建逻辑解耦。
  • 支持 layers 注入（如埋点、统计、权限等包装层）。
  • 组件缺失时降级为 DowngradeComponent（可打点上报）。

# 2.5 sdk（@xy/tms-sdk）

职责：搭建工作台——左侧物料面板、中间画布、右侧属性面板、工具栏（撤销/重做/保存/发布等），以及画布数据的托管与变更。

核心模块：

  • FrameworkContextProvider / Framework：提供 viewData、materialList、materialSchema、materialComponents、renderer、dndHooks 等，并初始化 ViewDataEngine。
  • ViewDataEngine（FrameworkData/ViewDataEngine.ts）：单例，托管 viewData 与 pageInfo，实现：
    • 撤销/重做（timeline 历史）
    • 自动保存（autoSave 定时）
    • 订阅：jump:status、autoSave、change、editing:change、material:updateProp 等
  • panel-materials：左侧物料列表。
  • panel-preview：中间画布，与 render 结合，可拖拽排序、选中。
  • panel-editor：右侧属性面板，根据当前选中物料的 schema 渲染 Form（SetterFactory/SchemaForm）。
  • panel-editor-field：表单项封装，对外暴露 Field 等。
  • tree：树形 viewData 的增删改、拖拽落点、子容器等。

数据流：用户拖拽/编辑 → 更新 viewData → ViewDataEngine 写回并触发 autoSave/change → 业务可订阅并持久化（如 requestPageUpdate）。

# 2.6 space-material-layers（@xy/space-material-layers）

职责：物料图层与协议空间，提供与渲染器配合的“层”能力（如样式容器）。

入口：src/index.ts 导出 StyleContainer（含 schema、layer）。render 的 ViewItemRender 会用 layers 对每个物料实例再包一层，这里提供的是 layer 的协议与实现。

# 2.7 space-materials（@xy/space-materials）

职责：微前端主应用，承载具体业务页面（含搭建页、预览页等）。通过 @xy/micro-fe-sdk 做路由与子应用加载，不直接实现物料，而是引用 materials、sdk、render 等。

# 三、设计原理

# 3.1 协议驱动

  • 类型与协议集中在 @xy/tms-type：MaterialSchema、MaterialViewData、MaterialInfo、PageInfo 等。
  • 物料通过 MaterialDescription + ViewSchema 描述“是什么、怎么配、怎么渲染”。
  • 渲染器只认 viewData + materialComponents，不关心搭建从哪来。

# 3.2 数据与视图分离

  • viewData：JSON 可序列化的页面结构（id、componentType、props、children）。
  • materialComponents：componentType → 实际 React 组件的映射。
  • 搭建端修改 viewData → 渲染端用同一份 viewData 驱动页面，实现编辑与预览一致。

# 3.3 工作台与渲染解耦

  • sdk 负责：画布交互、物料面板、属性面板、ViewDataEngine（历史、保存、事件）。
  • render 只负责：根据 viewData 和 materialComponents 渲染视图。
  • 同一套 render 可用于搭建态预览和线上 H5/小程序。

# 3.4 物料生命周期（SpaceMaterialSchema）

在 types 的 SpaceMaterialSchema 中扩展了生命周期与校验：

  • beforeDropped：拖入前拦截。
  • onInit：物料初始化时（如设默认值）。
  • onSave / onPublish：保存/发布前校验或打点。
  • onCopy / onDelete：复制/删除前拦截。
  • validators：实时校验。

# 四、流程说明

# 4.1 搭建页初始化

  1. 业务（如 space-materials）提供初始 viewData、materialList、materialSchema、materialComponents。
  2. sdk 的 FrameworkContextProvider 接收上述数据，初始化 ViewDataEngine（viewData、pageInfo）。
  3. 左侧 panel-materials 根据 materialList 展示可拖拽物料。
  4. 中间 panel-preview 使用 render，传入当前 viewData 与 materialComponents，渲染画布；可拖拽、选中。
  5. 右侧 panel-editor 根据当前选中项的 ViewSchema 渲染表单（Setter），修改写回 viewData。

# 4.2 拖拽添加物料

  1. 从 materialList 拖到画布，由 sdk tree 的 dnd 计算落点（容器、顺序）。
  2. 若配置了 beforeDropped，先执行；返回 false 则中止。
  3. 根据物料 ViewSchema 的 propsDefaultValue 生成新节点（id、componentType、props），插入 viewData。
  4. ViewDataEngine 更新 viewData，触发 change/autoSave，画布重渲染。

# 4.3 属性编辑

  1. 用户选中画布上某物料，sdk 将当前 viewItem 写入 editing 状态。
  2. 右侧根据 materialSchema[componentType]（即 ViewSchema）渲染 propsSchema（Field + Setter）。
  3. 用户修改表单项 → Setter 通过 Form 回调更新 viewData 中该节点的 props（或 setPropsByPath / batchUpdateProps）。
  4. ViewDataEngine 更新后触发 material:updateProp 等，画布与表单同步更新。

# 4.4 保存与发布

  1. 用户点击保存/发布，业务可订阅 ViewDataEngine 的 autoSave 或自行请求保存接口，将 viewData（及 pageInfo）提交后端。
  2. 若物料实现了 onSave / onPublish，可在保存/发布前做校验或打点，返回 false 可阻止操作。

# 4.5 预览与线上渲染

  1. 搭建态预览：sdk 已把当前 viewData 传给 render，所见即所得。
  2. 线上 H5/小程序：从接口拉取保存后的 viewData（及 pageInfo），再传入 render + materialComponents（及可选 layers），仅做渲染，无拖拽与属性面板。

# 六、文档与扩展

  • 各子项目根目录下的 README.md 提供该包的本地开发、构建、发布说明。
  • sdk/README.md 含工作台初始化、ViewDataEngine 事件与 API、物料协议说明。
  • 新增物料：在 materials 中新增 materialsComponents/<名称>/，实现 tms.ts + view-schema + View 组件，并在 src/index.ts 导出。
  • 新增 Setter：在 setter 中实现并导出，在物料的 ViewSchema.propsSchema 中引用。

以上为当前工作区的项目划分、设计原理与主流程说明，便于后续维护与扩展。

# 七、可优化与不足

结合代码与架构现状，以下为可优化点与已知不足，便于排期改进。

# 7.1 技术债务与废弃 API

  • 废弃未收敛：多处 @deprecated 仍在使用或未替换（如 types 中 uncopyable→copyable、setter 的 useFormContext 迁移到 sdk、materials 的 ContainerProps 等），建议列出迁移表并逐步替换。
  • TODO/FIXME 未闭环：
    • relationTree：types 中 $DATA.relationTree 标为实验、sdk 中仍依赖业务自定义 props.groups，待统一数据源与计算时机（sdk Framework 中有 “TODO: 根据分组容器组件传递 parentId 计算得到关系树”）。
    • ViewDataEngine：restoreByJumpIndex 内“根据 diff 和 store 动态计算”未实现；timeline 超长时的裁剪逻辑有 @todo。
    • 物料侧：ImageEditor 抠图 API、SourceMaterialModal 提交时弹窗关闭（FIXME）等待实现或修复。
  • 命名与分类：如 HeaderNavigation 的 category: 'category_deprecated'，需明确是下线还是迁移到新分类。

# 7.2 ViewDataEngine 单例与多实例

  • 单例限制：ViewDataEngine 为全局单例，多页面/多 Tab/微前端多子应用同时开多个搭建页时，会共用一个引擎，导致数据与撤销栈串台。
  • 建议：支持“按页面/按应用”的引擎实例（例如通过 Context 注入实例，或 getInstance(key)），并在页面卸载时调用 destroy，避免内存与事件残留。

# 7.3 依赖与版本管理

  • @xy/tms-type 版本不一致：materials/sdk/render 用 ^0.0.20，space-material-layers 用 ^0.0.19，setter 的 dependencies 为 ^0.0.8，易导致类型与协议不一致。
  • resolutions 使用较多：多包用 resolutions 锁版本，升级时容易连锁冲突，建议在 monorepo 或统一版本策略下收敛。
  • 协作成本：当前多仓库/多包独立发版，types 变更需协调各包升级，建议明确 types 的 breaking 发布规范与各包依赖范围（如 type 用 minor 表示不兼容）。

# 7.4 测试与质量

  • 测试覆盖不足：仅 sdk 有 __test__ 与 ViewDataEngine 单测，materials/render/setter 缺少单测与集成测，回归成本高。
  • 建议：为 ViewDataEngine、tree 的增删改与拖拽、render 的 ViewItemRender/ContainerRender 补充单测；关键流程（拖入→编辑→保存）做少量 E2E 或集成测。

# 7.5 文档与规范

  • README 不完整：render 的 README 几乎为空；sdk README 中“国际化”等为待补充。
  • 物料/Schema 规范：propsSchema 既有“描述对象”又有“React 组件”（如 Field + Setter），新物料开发心智不统一，建议在文档中明确推荐写法（如以 Schema 描述为主、复杂区块用自定义组件）。
  • 架构文档：可在各子项目 README 中增加“在本体系中的角色”和指向本架构文档的链接。

# 7.6 数据与校验

  • viewData 校验：保存/发布前若仅依赖各物料 onSave/onPublish，缺少对整棵 viewData 的 schema 校验（如必填、结构合法性），易产生脏数据。
  • 建议：定义 viewData 的 JSON Schema（或基于 types 生成），在提交前做一次整体校验；与物料 validators 配合使用。

# 7.7 性能与体验

  • 撤销栈：MAX_TIMELINE_LENGTH = 50 固定，不可配置；大页面下 300ms 内的合并策略可能仍产生较多历史节点，可考虑按“操作类型”或“时间+数量”做更可控的合并与上限配置。
  • 大列表：画布或物料列表在 viewData 很大时是否有虚拟滚动或按需渲染未在代码中明确体现，可评估大页面下的性能与交互。

# 7.8 安全与环境

  • 环境隔离：example/mock 中部分写死 test 域名（如 img.test.linkiebuy.com），建议通过环境变量或配置统一注入，避免误发到生产。

以上为当前方案的主要可优化点与不足，可按优先级（稳定性 > 多实例/依赖 > 测试/文档 > 性能/体验）逐步迭代。
