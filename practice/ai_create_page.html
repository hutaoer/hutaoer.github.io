AI 生成网页功能 - 步骤说明

# AI 生成网页功能 - 步骤说明

本文档详细说明项目中「AI 生成网页」功能的每个步骤，包括完整生成流程与增量修改流程的设计原理、输入输出及关键逻辑。

# 一、功能概览

AI 生成网页的核心是：用户用自然语言描述需求 → 系统生成符合 PageDescriptor 规范的 JSON 配置 → 前端按 Schema 渲染为实际页面。

整体由两条主流程组成：

  1. 完整生成流程：从零根据用户描述生成整页 Schema。
  2. 增量修改流程：在已有 Schema 基础上，根据用户修改描述做局部更新。

两条流程均基于 LangGraph 有状态工作流，状态在节点间流转，支持条件分支与循环。

# 二、Dify 在流程中的作用

Dify 在本项目里充当 API 知识库，用于在生成页面 Schema 时做 RAG（检索增强生成），让 LLM 能「看到」当前环境、业务系统下的真实接口信息，从而生成可正确绑定接口的配置。

# 2.1 角色概览

环节 作用
写入 业务系统绑定 Dify 知识库（difyDatasetId）；Swagger 导入后同步到 Dify，将接口文档（方法、路径、参数、说明等）写入知识库。
检索 用户描述需求后，用查询（或优化后的检索句）去 Dify 做向量/混合检索，取回与需求相关的 API 文档片段。
注入 检索结果格式化为 ragContext 文本，注入到 Schema 生成 时的 system prompt（{ragContext} 占位符），供 LLM 参考。

因此：Dify 不参与对话本身，也不直接生成 Schema，而是为「生成」步骤提供「该用哪些 API、接口长什么样」的上下文。

# 2.2 在生成流程中的位置

  • LangGraph 工作流 里的 api_selection 节点当前是模拟实现（按 intent 构造假 API）；设计上可改为：先调 ChatRagService.retrieveContext，用 Dify 检索到的 API 作为 selectedApis / ragContext，再进入 schema_generate。
  • Chat 模块（chat.service.ts）在「生成模式」下会先判断是否需要检索；若需要，则调用 ChatRagService.retrieveContext(searchQuery, systemId)，得到 ragResults 后格式化为 ragContext，再拼进生成用的 system prompt（如 createTemplateAwarePrompt、createSchemaGenerationPrompt 等）。Schema 生成节点若在 Chat 驱动下执行，使用的就是这份已带 RAG 上下文的 prompt。

数据流可简化为：

用户描述 → Chat 判定为生成 → ChatRagService.retrieveContext(query, systemId)
    → DifyRetrievalService.retrieve({ query, datasetId }) → Dify API /datasets/:id/retrieve
    → 返回相关文档片段 → formatContextForPrompt() → ragContext 字符串
    → 注入到 Schema 生成的 system prompt → LLM 生成带正确 API 绑定的 Schema

# 2.3 知识库组织与同步

  • 按业务系统分库：每个业务系统可绑定一个 Dify 知识库（difyDatasetId），实现「环境 + 系统」维度的隔离。
  • 同步内容：Swagger 解析后的 API 会以文档形式写入对应 Dify 知识库（当前实现多为「每系统一个文档」，文档内包含该系统下的 API 列表与元数据；也可设计为每 API 一条文档以便更细粒度检索）。
  • 可选扩展：除 API 外，模板/组件物料文档也可同步到 Dify，用于组件选型或说明的 RAG（与「生成网页」主流程中的 API 检索是互补关系）。

# 2.4 相关代码与配置

用途 路径/说明
Dify 检索封装 apps/api/src/modules/schema-generator/generation/dify-retrieval.service.ts
Chat 侧 RAG 调用与格式化 apps/api/src/modules/chat/chat-rag.service.ts（retrieveContext、formatContextForPrompt）
生成 Prompt 中的 RAG 占位 apps/api/src/modules/chat/prompts/generate/*.ts 中的 {ragContext}
业务系统绑定知识库 业务系统实体含 difyDatasetId；同步与绑定见 doc/schema-generator/Dify-知识库集成-设计.md

总结：Dify 的作用是 在 AI 生成网页流程中提供「API 知识库」：根据用户需求检索相关接口文档，并把结果注入到 Schema 生成的 prompt 中，使生成的页面配置能正确绑定到真实 API（路径、方法、参数等），而不是仅靠 LLM 臆造接口。

# 三、完整生成流程（步骤详解）

# 流程总览

用户输入 → patch_analysis → clarify → intent_analysis → api_selection → schema_generate → schema_validate
                                                                                ↑                    ↓
                                                                                └── schema_repair ←─┘

以下按执行顺序说明每个节点。

# 步骤 1：Patch 分析（patch_analysis）

位置：apps/api/src/modules/schema-generator/workflow/nodes/patch-analysis.node.ts

职责：判断当前请求是「增量修改」还是「全新生成」，决定走完整生成还是增量修改子流程。

输入：

  • userInput：用户原始输入
  • finalSchema：当前会话已有的 Schema（若有，通常由调用方传入）

逻辑：

  1. 若没有 finalSchema，直接判定为全新生成，isPatchMode = false。
  2. 若有 finalSchema，优先用 LLM 判断：
    • 增量修改特征：明确提到「修改/改成/更新/调整/替换」等动词，且针对具体字段或组件（如「把标题改成…」「第一个卡片的颜色改为…」）。
    • 全新生成特征：使用「创建/生成/做一个/新增页面」等，或描述完整页面需求、整体重新设计。
    • 规则：仅当用户明确说「把 XXX 改成 YYY」这类局部修改时才判为增量。
  3. LLM 失败时降级为关键词规则：
    • 若包含「创建、生成、做一个、新建…」→ 全新生成。
    • 增量需同时包含：修改类动词（修改、改成、更新…）+ 具体目标（第一个、标题、颜色、widget…）。

输出：

  • metadata.isPatchMode：true 走增量修改，false 走完整生成。
  • 若为 patch，还可有 patchTarget、patchOperation 等，供后续节点使用。

分支：

  • isPatchMode && finalSchema → 进入 patch_generate（增量修改分支）。
  • 否则 → 进入 clarify（完整生成分支）。

# 步骤 2：需求澄清（clarify）

位置：apps/api/src/modules/schema-generator/workflow/nodes/clarify.node.ts

职责：检查用户输入是否包含足够信息；若不足则生成澄清问题并暂停工作流，等待用户补充。

输入：

  • userInput
  • collectedInfo（若之前已有澄清轮次）
  • metadata.userClarified（用户是否已补充信息）

逻辑：

  1. 若 collectedInfo.hasSufficientInfo 或 metadata.userClarified，直接通过，不提问。
  2. 快速规则检测：
    • 用 quickTemplateDetect 推测模板类型（如 Dashboard、CRUD、Form）。
    • 用 quickCompletenessCheck 按模板类型检查必要信息是否齐全。
  3. 若快速检查通过且置信度 ≥ 0.8，标记信息充足，继续流程。
  4. 否则调用 LLM 深度检查（REQUIREMENT_COMPLETENESS_CHECK_PROMPT）：
    • 按页面类型检查必要项（如 Dashboard：用途、数据类型、角色；CRUD：实体、操作、列表字段等）。
    • 返回 status：complete / incomplete / need_type，以及 missingInfo、detectedPageType、confidence。
  5. 若仍为 incomplete 或 need_type：
    • 优先用预定义澄清模板（如页面类型多选 <choice>）。
    • 否则用 LLM 生成澄清问题，或降级为通用提示。
    • 设置 metadata.needsClarification = true、metadata.clarificationMessage。

输出：

  • 信息充足：collectedInfo（含 hasSufficientInfo、detectedPageType 等），进入 intent_analysis。
  • 需澄清：needsClarification = true，工作流 END，由上层将 clarificationMessage 返回用户，待用户回复后再次进入工作流。

# 步骤 3：意图分析（intent_analysis）

位置：apps/api/src/modules/schema-generator/workflow/nodes/intent-analysis.node.ts

职责：从用户描述中识别页面类型、模板、实体、操作、功能等，为后续 API 选择与 Schema 生成提供结构化意图。

输入：userInput（及上一步的 collectedInfo 等）。

逻辑：

  1. 若有 Langchain 服务，优先 LLM 分析：
    • 输出 JSON：pageType、operations、features、entities、confidence。
    • 约定：列表/管理/CRUD → crud-list；详情/查看 → detail；表单/创建/编辑 → form-only；仪表盘/统计/图表/工作台 → dashboard。
    • 若 LLM 未返回 template，用 mapPageTypeToTemplate 将 pageType 映射到模板名（如 dashboard → DashboardTemplate）。
  2. 降级：LLM 失败时用关键词规则匹配 pageType 和 template，并简单提取实体、操作、功能关键词。

输出：

  • intent：IntentAnalysis，包含：
    • pageType：crud-list | detail | form-only | dashboard | config | wizard | custom
    • template：如 DashboardTemplate、CrudTemplate、FormTemplate 等
    • entities：如 ['User','Order']
    • operations：如 ['create','update','delete','list']
    • features：如 ['search','filter','pagination']
    • confidence：0–1

下一步：固定进入 api_selection。

# 步骤 4：API 选择（api_selection）

位置：apps/api/src/modules/schema-generator/workflow/nodes/api-selection.node.ts

职责：根据意图中的实体与操作，选定要绑定的 API（列表、创建、更新、删除等），供 Schema 生成时填写 apis 与 bindings。

输入：intent（含 entities、operations）。

逻辑：

  • 当前实现为模拟选择：按 intent.operations 构造 list/create/update/delete 等接口的 method、url、description。
  • 设计上预留接入 ChatRagService 做真实 RAG 检索（如 Dify 知识库、环境/系统/apiType 过滤）。

输出：

  • selectedApis：如 { list: {...}, create: {...}, update: {...}, delete: {...} }。

下一步：固定进入 schema_generate。

# 步骤 5：Schema 生成（schema_generate）

位置：apps/api/src/modules/schema-generator/workflow/nodes/schema-generate.node.ts

职责：在模板规范约束下，用 LLM 生成符合 PageDescriptor 的 JSON；失败时降级为模板填充。

输入：

  • userInput、intent、selectedApis
  • ragContext（若上游有 RAG 检索结果，可注入为 API 上下文）

逻辑：

  1. 加载模板上下文：
    • 通过 MaterialsContextService.getTemplateContext(intent.template) 获取该模板的规范说明（SKILL.md + types.ts 等）。
    • 模板上下文会写入 system prompt，约束生成格式与字段。
  2. LLM 生成：
    • System：天剑 Schema 生成器角色 + 模板上下文 + 生成规则（schemaVersion 2.0、meta.pageType、apis、columns/formFields、bindings、dashboard 仅用 Widget 目录中的 type 等）。
    • User：用户需求 + 意图摘要（页面类型、实体、操作、功能）+ 可选 RAG API 上下文。
    • 要求直接输出 JSON，无注释、无尾逗号、键名双引号；数值/颜色/布局等类型有明确约束。
  3. 解析与基本校验：
    • 从 LLM 回复中提取 JSON（代码块优先，其次含 schemaVersion 的对象，再次括号匹配）。
    • 强制存在 schemaVersion、components；若为 dashboard 则需有 components.widgets。
  4. 降级：若 LLM 解析失败或校验不通过，则用模板填充生成最小可用 Schema（如 Dashboard 的 banner+stats+lineChart 结构，或通用 meta + apis + columns/formFields/actions）。

输出：

  • draftSchema：JSON 字符串形式的 PageDescriptor。
  • templateContext：写入 state，供校验/修复节点使用。

下一步：固定进入 schema_validate。

# 步骤 6：Schema 校验（schema_validate）

位置：apps/api/src/modules/schema-generator/workflow/nodes/schema-validate.node.ts
校验器：apps/api/src/modules/schema-generator/validation/schema-validator.ts

职责：解析 draftSchema，执行基础规则与模板规则校验；通过则写回 finalSchema 并结束，不通过则进入修复或失败。

输入：draftSchema、intent.template。

逻辑：

  1. JSON 解析：若解析失败，直接返回 parse_error 类错误。
  2. SchemaValidator.validate：
    • 基础规则（base.rules）：如 schemaVersion 必为 "2.0"、meta 及 meta.pageType 必填、pageType 枚举合法、apis 结构、components 结构等。
    • 模板规则：若为 DashboardTemplate/dashboard，执行 dashboard.rules（如 widgets 存在、widget type 合法、layout/span 范围、数值/颜色等）。
    • 软风险（可选）：如图表数据过少、列表 items 为空、缺少 header、首行未占满等，记为 warning。
  3. 风险评分：根据错误/警告类型与数量计算 0–1 风险分（仅用于观测与后续扩展）。

输出：

  • 无错误：validationErrors = []，finalSchema = parsedSchema，completed = true → END。
  • 有错误且 metadata.retryCount >= MAX_REPAIR_ROUNDS（默认 3）→ END（失败）。
  • 有错误且未超修复轮次 → 进入 schema_repair。

# 步骤 7：Schema 修复（schema_repair）

位置：apps/api/src/modules/schema-generator/workflow/nodes/schema-repair.node.ts

职责：根据校验错误对 draftSchema 进行自动或 LLM 修复，然后再次进入 schema_validate，形成闭环。

输入：validationErrors、draftSchema、templateContext、metadata.retryCount。

逻辑：

  1. 增加重试计数：retryCount + 1。
  2. 规则自动修复（按错误类型）：
    • required_field_missing：补 schemaVersion、meta.pageType 等。
    • invalid_value：如 percent 超范围则缩放到 0–1。
    • invalid_widget_type：移除无效 widget 等。
  3. 若规则修复成功，直接返回新的 draftSchema，下一轮再进入 schema_validate。
  4. 若无法规则修复，则 LLM 修复：
    • 将错误列表（位置、消息、建议）与当前 Schema、模板规范一并发给 LLM，要求只修正错误并输出完整 JSON。
    • 解析并校验修复后 JSON 的完整性（schemaVersion、components），成功则返回新 draftSchema。
  5. 若仍失败，仍返回当前 draftSchema 并增加 retryCount，由下一轮 schema_validate 决定是否已达 MAX_REPAIR_ROUNDS 而结束。

输出：

  • 更新后的 draftSchema 与 metadata.retryCount，边指向 schema_validate，形成「校验 → 修复 → 再校验」循环，最多 MAX_REPAIR_ROUNDS 轮。

# 完整生成流程 - 小结

步骤 节点 主要作用
1 patch_analysis 判断增量 vs 全新，无 finalSchema 必走完整生成
2 clarify 检查需求是否充足，不足则提问并暂停
3 intent_analysis 识别 pageType、template、entities、operations、features
4 api_selection 选定 list/create/update/delete 等 API（当前为模拟，可接 RAG）
5 schema_generate 按模板规范 + LLM 生成 PageDescriptor，失败则模板降级
6 schema_validate 规则校验，通过则输出 finalSchema 并结束
7 schema_repair 自动/LLM 修复错误，再回到校验，最多 3 轮

# 四、增量修改流程 - 各步骤详解

当 patch_analysis 判定为增量修改且存在 finalSchema 时，主流程会先走 patch_generate（主流程内简单版），而独立增量修改工作流则用于对话场景下「在已有页面上改一点」的完整链路，包含意图分析、检索、生成、用户决策、应用等。

下面说明两处：主流程中的 patch_generate，以及独立工作流中的各节点。

# 主流程中的增量分支：patch_generate（简单版）

位置：apps/api/src/modules/schema-generator/workflow/nodes/patch-generate.node.ts

职责：在已有 finalSchema 基础上，按用户修改描述生成「整份修改后的 Schema」，而不是 JSON Patch。

输入：userInput、finalSchema、metadata.patchTarget（可选）。

逻辑：

  • 调用 LLM：角色为「Schema 增量修改专家」，原则为最小化修改、保持结构、不自创字段、输出完整 JSON。
  • User 消息包含：用户修改需求、目标路径（若有）、当前 Schema 全文。
  • 从回复中提取 JSON，校验 schemaVersion、components 存在。

输出：更新后的 draftSchema，随后进入 schema_validate，与完整生成共用校验与修复逻辑。

# 独立增量修改工作流（Patch Workflow）

入口：LangGraphWorkflowService.executePatchWorkflow / executePatchWorkflowStream
图定义：buildPatchWorkflow()，节点顺序为：

patch_intent_analysis → patch_search → patch_generate（带重试）→ [user_decision | patch_apply | end]

使用场景：对话中用户对当前页面的「修改/改成/调整」类请求，且需要检索 Schema 节点、规则、物料，并支持用户决策（选方案、重试、澄清等）后再应用。

# 步骤 P1：Patch 意图分析（patch_intent_analysis）

位置：apps/api/src/modules/schema-generator/workflow/nodes/patch-intent-analysis.node.ts

职责：从用户修改描述中抽取 target、property、action、newValue、searchQuery 等，供检索与生成使用。

逻辑：LLM + 固定 JSON 格式，输出 ModificationIntent 及用于检索的 searchQuery；失败时降级为简单默认（如 target=用户原文、action=modify）。

输出：modificationIntent、patchSearchQuery 等，进入 patch_search。

# 步骤 P2：Patch 检索（patch_search）

职责：根据 patchSearchQuery 和当前 Schema 的 ETag，检索可用的节点、规则、物料（如 Schema 片段、字段规则），并格式化为后续 LLM 可用的上下文。

输出：searchResults、searchResultsFormatted、currentEtag 等，进入 patch_generate（带重试）。

# 步骤 P3：Patch 生成（带重试与用户决策）（patch_generate）

位置：含 patch-generate-retry.node.ts 等

职责：在检索上下文基础上，生成 JSON Patch 或修改后的 Schema，并进行 dry-run 校验；若需用户选择方案或重试，则设置 needUserDecision 与 userOptions。

逻辑：可能多轮重试、调用 Skill 与工具；校验不通过或存在多方案时，进入 user_decision，否则进入 patch_apply 或 end。

# 步骤 P4：用户决策（user_decision）

职责：等待用户选择（例如选择某一方案、重试生成、或回到澄清）。决策结果通过 submitUserDecision 写入 state，工作流根据 nextNode 跳转到 patch_generate、patch_intent_analysis 或 end。

# 步骤 P5：Patch 应用（patch_apply）

位置：apps/api/src/modules/schema-generator/workflow/nodes/patch-apply.node.ts

职责：将已校验通过的 generatedPatches 通过 toolHandlers.handleApply 应用到当前版本（带 expectedEtag），持久化新版本并返回 newVersionId、newEtag、version。

输出：applyResult（success、newVersionId、newEtag、version 等），并发送 version_created 等事件，流程 END。

# 五、模板与校验体系

# 模板上下文

  • MaterialsContextService（apps/api/src/modules/chat/materials-context.service.ts）负责按模板名加载 SKILL.md、types.ts 等，并做缓存与文件监听。
  • getTemplateContext(template) 返回的字符串会注入到 schema_generate 和 schema_repair 的 system prompt，保证生成与修复都符合该模板的 PageDescriptor 约定。

# 校验规则

  • SchemaValidator 组合：
    • base.rules：schemaVersion、meta、pageType、apis、components 等通用规则。
    • dashboard.rules：widgets 存在性、widget type 白名单、layout、数值范围等。
  • 错误带 type、field/path、message、severity（error/warning）、suggestion，供 schema_repair 自动修复或 LLM 修复使用。

# 六、前端渲染

生成的 finalSchema（PageDescriptor）会传到前端的 SchemaRender 组件（materials/src/components/SchemaRender/index.tsx）。

  • 模式：direct（直接传 schema 对象）/ url / api（按版本 ID 拉取）。
  • 逻辑：根据 schema 的 meta.pageType 或模板类型选择 DashboardTemplate、CrudTemplate、EcommerceHomeTemplate、FreeformTemplate 等渲染；错误边界捕获渲染异常并展示友好错误信息。

即：AI 生成的是符合 PageDescriptor 的 JSON，真正「网页」由各模板组件根据该 JSON 渲染而成。

# 八、配置项摘要

  • MAX_REPAIR_ROUNDS：Schema 校验-修复循环上限，默认 3。
  • enableSoftRiskDetection：是否启用软风险（如数据过少、缺 header）检测。
  • requireHeader / requireFullRow：Dashboard 是否要求 header、首行是否需占满 24 列（影响 warning）。
